# Chat Events — PlexonChats 3.4.0

Chat Events are server competitions managed by one coordinator with at most one globally active run. PlexonChats 3.4.0 preserves the accepted 3.3.0 exact-winner architecture and adds structured presentation, persistent win statistics, a full administration GUI and a dedicated interactive Bingo engine.

## Master and scheduler

```yaml
chat-events:
  enabled: true
  scheduler:
    enabled: true
    initial-delay-seconds: 180
    min-interval-seconds: 600
    max-interval-seconds: 1200
    min-online: 1
    avoid-immediate-repeat: true
    pause-when-empty: true
```

`chat-events.enabled` is the persistent master. `scheduler.enabled` controls only automatic scheduling, so staff can still manually start events when automatic scheduling is disabled. `/chat events pause` and `/chat events resume` are runtime scheduler controls.

There is one coordinator, no scheduler allocation per ordinary chat message, and no per-player Bingo repeating task.

## Event types

PlexonChats 3.4.0 supports:

```text
TYPE
UNSCRAMBLE
MATH
TRIVIA
REVERSE
BINGO
```

The first five are answer events generated by the normal `ChatEventEngine` and are won through accepted native public chat. `BINGO` is a separate multi-phase event and does not use typed-answer matching.

Fresh v6 defaults include:

```text
type-rush
unscramble
math-normal
math-hard
trivia
reverse
bingo-classic
```

## Ordinary answer-event lifecycle

```text
SCHEDULED -> ACTIVE -> WON | TIMED_OUT | CANCELLED
```

A run owns a unique run ID, definition, prompt data, accepted answers, eligible-player snapshot, monotonic deadline and exact-once winner/reward state.

Only accepted native Minecraft public chat in an allowed LOCAL/GLOBAL channel may win. Console, `/g`/`/l` synthetic command sends, PMs, Discord-origin traffic, broadcasts, auto-messages and plugin-generated messages do not count.

The synchronous cancellable `PlexonChatEvent` remains authoritative before answer acceptance.

## Answer normalization

```yaml
chat-events:
  defaults:
    matching:
      case-sensitive: false
      trim: true
      collapse-whitespace: true
      unicode-normalization: NFKC
      ignore-diacritics: false
```

Answers are data only. They are never trusted MiniMessage and are never available as console-command reward placeholders.

## Presentation

Event cards are configured as line lists:

```yaml
chat-events:
  presentation:
    blank-lines-before: 1
    blank-lines-after: 1
    separator: "<dark_gray>━━━━━━━━━━━━━━━━━━━━━━━━━━━━</dark_gray>"
    type-names:
      TYPE: "Type Rush"
      UNSCRAMBLE: "Unscramble"
      MATH: "Quick Math"
      TRIVIA: "Trivia"
      REVERSE: "Reverse"
      BINGO: "Bingo"
    start:
      - "{separator}"
      - "<gradient:#55ffff:#1597ff><bold>CHAT EVENT</bold></gradient> <aqua>{event_name}</aqua>"
      - ""
      - "<white>{prompt}</white>"
      - ""
      - "<gray>Reward:</gray> <gold>{reward}</gold>"
      - "<gray>Time:</gray> <yellow>{duration_seconds}s</yellow>"
      - "{separator}"
```

`blank-lines-before` and `blank-lines-after` accept 0–3. Empty lines are sent as real empty Adventure Components and only to the relevant event audience.

Safe placeholders include event identity/type/name, prompt/description, reward, duration/remaining time, winner/UUID, persistent total/type wins, elapsed time, answer, participant count and Bingo draw values. Dynamic player/provider content is inserted as Components rather than parsed as markup.

## Event definitions

Example TYPE event:

```yaml
chat-events:
  events:
    type-rush:
      enabled: true
      name: "Type Rush"
      type: TYPE
      weight: 12
      cooldown-seconds: 1800
      reward-profile: basic
      values: ["bingo", "plexon", "diamond", "redstone"]
      prompt: "<gray>Type <yellow>\"{value}\"</yellow> before anyone else!</gray>"
```

Definitions can configure enabled state, display name, weight, cooldown, reward profile, duration/min-online, permission/world audience and accepted channels. `weight: 0` is manual-only. Manual starts still obey event enabled state, cooldown and eligibility checks.

MATH supports `ADD`, `SUBTRACT`, `MULTIPLY`, and exact integer `DIVIDE`. TRIVIA requires explicit question/accepted-answer entries. REVERSE uses Unicode code points. UNSCRAMBLE generation is bounded.

## Rewards

Reusable profiles may combine Vault economy, optional PlexonKeys and trusted console commands:

```yaml
chat-events:
  reward-profiles:
    epic:
      economy:
        enabled: true
        amount: 5000.0
      plexonkeys:
        enabled: true
        tier: EPIC
        amount: 1
      console-commands: []
```

A winner is selected atomically. One independent reward guard allows exactly one bundle attempt. A failed component does not select another winner or reopen the run.

## Persistent win statistics

Confirmed winners are recorded in `plugins/PlexonChats/chat-events.db` with total/type/definition counts and immutable history. The database enforces unique `run_id`; duplicate completion callbacks cannot double-count.

The immediate winner message uses the in-memory updated counter while the confirmed write executes on the dedicated database executor. Normal chat never queries SQLite.

See [CHAT-EVENT-STATS.md](CHAT-EVENT-STATS.md).

## Bingo

Bingo occupies the same single active-event slot but uses:

```text
JOINING -> ACTIVE -> WON | TIMED_OUT | CANCELLED
```

The server sends one general clickable join announcement. Players explicitly opt in to the exact run. Only joined participants receive boards, repeated draws and mark feedback. Non-participants receive no repeated number traffic.

Each participant has one server-generated traditional 75-ball 5×5 card. Clickable cells submit a run ID and cell index only; the server resolves and validates the board number and draw state. Supported patterns are ROW, COLUMN, DIAGONAL, FOUR_CORNERS and FULL_HOUSE.

See [BINGO.md](BINGO.md).

## Commands

Player/read surface:

```text
/chat events
/chat events status
/chat events list
/chat events stats
/chat events stats <player>
/chat events leaderboard
/chat events bingo join <run-id>
/chat events bingo card
```

Staff management:

```text
/chat events enable
/chat events disable
/chat events pause
/chat events resume
/chat events start <id|random>
/chat events stop
/chat events preview <id>
/chat events bingo status
/chat events bingo participants
```

The internal Bingo mark command is intentionally not advertised and is revalidated completely server-side.

## GUI

For players, `/chat events` opens a live dashboard. Console receives text status.

Pages:

```text
Dashboard
Events browser
Event details
Rewards
Bingo
Statistics
```

The event browser is paginated. Left click opens details, right click previews, and shift-left manually starts. Inventory transfers/drags remain blocked. Every action rechecks permission and the holder's config revision; active-event controls also carry run identity so an old inventory cannot stop a newer run.

## Diagnostics

`/chat diagnostics` includes master/scheduler/coordinator state, active run, last result/winner, reward integrations, database file/schema/executor/pending writes/failures, recorded/cached statistics, and Bingo phase/participant/draw state.

## Reload and migration

3.4.0 uses `config-version: 6`. Valid older configurations are backed up as `config-before-v6-<timestamp>.yml` before migration.

`chat-events.events` is administrator-owned during migration. Event IDs are opaque identifiers. A v5 TYPE definition whose ID is `bingo` remains a TYPE definition after migration and is never silently converted into real Bingo.

Invalid presentation, MiniMessage, reward, event, Bingo or GUI values reject the complete candidate. The previous live runtime stays active after a rejected reload.
